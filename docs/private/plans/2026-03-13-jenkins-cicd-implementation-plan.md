# Jenkins CI/CD Implementation Plan

## Goal

Plan a simple Jenkins-based CI/CD implementation for `rozliczPWS` using the existing self-hosted Jenkins setup, the current repository pipeline, and `Jenkinsfile_reference` from another working project as a reference when creating the new `Jenkinsfile`.

## Current state

The repository already has a working `Jenkinsfile` with:
- checkout,
- Composer install,
- npm install,
- production asset build,
- `php artisan test`,
- deploy on `master`,
- rollback through `RUN_ROLLBACK`.

The project also already has:
- a private decision to use Jenkins in Docker,
- private manuals for Jenkins install, release flow, and dependency updates,
- a Laravel Mix based frontend build,
- a green automated test suite.

`Jenkinsfile_reference` shows a more mature pipeline shape with:
- a dedicated builder agent label,
- concurrency and retention controls,
- agent tooling validation,
- explicit CI environment preparation,
- manual production approval,
- stronger branch/change-request gating,
- staging and production separation,
- container-image build and registry push flow.

For this repository, the reference should be used selectively while creating a new `Jenkinsfile`. The application should keep a simple SSH deployment model with in-place deployment, so registry, image-build, release-symlink, rollback, and multi-environment container rollout parts from the reference should not be copied.

## Scope

- Plan Jenkins-first CI/CD for this repository
- Use `Jenkinsfile_reference` as the main structural reference for the new `Jenkinsfile`
- Keep the implementation junior-friendly and limited to necessary stages only
- Cover CI, CD, credentials, builder-agent requirements, and deployment layout
- Avoid optional stages unless they clearly improve reliability

Out of scope for the first implementation pass:
- switching deployment to Docker Compose or Kubernetes,
- adding container registry build/push flow,
- replacing Jenkins with GitHub Actions,
- introducing staging,
- major application refactors unrelated to pipeline reliability.

## Assumptions

- Jenkins itself runs in Docker on the server.
- A Linux build agent already exists and the pipeline should use the same label as in the `gerwazy` project: `docker-builder`.
- Production deploy target is a single host only.
- The current application root on the production server is `<deploy-path>`.
- The production database already exists on the server and is named `<production-database>`.
- The first implementation should optimize for reliability and clarity, not for a multi-environment rollout.
- The production `.env` file will continue to live on the server and point to the existing database instead of being generated by Jenkins.
- Deployment should happen in place in `<deploy-path>` without release symlinks and without automated rollback.

## Steps

1. Replace the generic pipeline shell with a builder-specific baseline from `Jenkinsfile_reference`.
   - Set the pipeline agent to `docker-builder`.
   - Add `buildDiscarder(...)` to keep Jenkins history under control.
   - Add `disableConcurrentBuilds()` to avoid overlapping deploys.
   - Add `skipDefaultCheckout(true)` if checkout remains explicit in the first stage.

2. Add builder-environment validation before install/build stages.
   - Verify presence of `php`, `composer`, `npm`, `ssh`, and `rsync`.
   - Verify required PHP extensions for Laravel tests and SQLite test execution.
   - Fail early with a readable message when the agent is misconfigured.

3. Keep the CI runtime environment simple.
   - Prefer reusing `.env.testing` and the current SQLite-based test approach for the first pass.
   - Do not introduce `.env.ci`, custom CI scripts, or runtime env generation unless Jenkins proves unable to run the current tests as-is.
   - Keep CI environment preparation much simpler than in `Jenkinsfile_reference`.

4. Reshape the pipeline to the minimum useful stage order.
   - `Checkout`
   - `Validate Agent Tooling`
   - `Install PHP Dependencies`
   - `Install Node Dependencies`
   - `Run Tests`
   - `Build Production Assets`
   - `Deploy (master only)`

5. Define the simple production deploy model.
   - Keep deploy branch-gated to `master`.
   - Keep deploy automatic on `master` to avoid unnecessary pipeline complexity in the first version.
   - Use `rsync` or `scp` to update the application in place under `<deploy-path>`.
   - Keep the production `.env` on the server and exclude it from deployment.
   - Preserve writable runtime directories such as `storage` and `bootstrap/cache`.
   - Run `composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction`, migrations, and Laravel cache warmup on the server after sync.
   - Use the existing production database through the server-side `.env`; Jenkins should not manage database provisioning.

6. Tighten credential and SSH handling.
   - Keep secrets in Jenkins Credentials and shared server files, not in repo.
   - Keep `deploy-ssh-key`, `deploy-host`, and `deploy-user` as the confirmed credential IDs.
   - Prefer a safer SSH host-key strategy than fully disabled verification if the server setup allows it.

7. Align documentation with the final implementation.
   - Update the private release manual when the final stage order is confirmed.
   - Add or update a private implementation report after the pipeline is implemented.
   - Update public CI/CD and deployment summaries only after the private implementation details are correct.
   - Remove references to rollback and release-symlink deployment from docs if the implementation no longer uses them.

8. Verify the implementation in controlled passes.
   - Run CI-only validation on a non-`master` branch.
   - Run a production deploy from `master` only after the CI part is stable.
   - Validate the deployed application manually after the first production run.

## Reference adoption map

Adopt from `Jenkinsfile_reference`:
- dedicated agent label,
- build retention,
- concurrency protection,
- explicit checkout,
- tooling validation,
- clearer branch gating.

Do not adopt in the first pass:
- container image build,
- registry push,
- multi-arch `buildx`,
- staging and production runtime env injection scripts,
- manual production approval,
- Docker-based application deployment model,
- release-symlink deployment,
- rollback stage,
- staging environment,
- deployment metadata artifacts.

## Risks

- Copying too much from `Jenkinsfile_reference` would overcomplicate a straightforward Laravel deployment.
- In-place deployment is simpler, but a failed production deploy will require manual recovery because there is no automated rollback.
- Replacing application files in place increases the importance of correct excludes for `.env`, `storage`, and generated runtime files.
- Automatic deploy on every push to `master` increases the need for reliable tests and cautious merges.
- SSH host verification disabled too broadly weakens the security story of the pipeline.
- A pipeline that depends on new CI environment files may become harder to maintain than the current Laravel test setup.

## Definition of done

- The repository has an approved private implementation plan for Jenkins-based CI/CD.
- The plan clearly states which parts of `Jenkinsfile_reference` should be reused and which should be skipped.
- The planned pipeline stages, builder label, credential model, in-place deploy model, and production path are explicit.
- The plan reflects the decision to skip rollback and release-symlink deployment in the first implementation.
